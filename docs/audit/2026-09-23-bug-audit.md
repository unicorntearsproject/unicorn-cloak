# Bug audit — 2026-09-23

A full read-through of `src/unicorn_cloak/` looking for correctness bugs,
with each suspect confirmed by an actual reproduction wherever one was
practical. This is a findings report only: nothing here has been fixed.

## Scope and method

- **Baseline:** commit `afd2ed0` (`main`, "Fix stale file-finish callback
  silently orphaning live playback…"). Line links below point at that
  revision. Uncommitted work in progress when the audit ran (the new
  "desktop" audio source in `audio_manager.py`, `config.py` and
  `control_panel_window.py`) was left out of scope, and line numbers in
  those three files will drift once that lands.
- **Test suite at baseline:** `.venv/bin/pytest` gives 503 passed, 0 failed.
  None of the bugs below are caught by the current suite.
- **Verification labels:**
  - **Reproduced** means a throwaway script built on the real classes (headless
    Qt, same as the test suite) showed the wrong behavior.
  - **Code-verified** means the path was traced by reading the code but not
    executed, usually because it needs a live OBS instance or a real mic.
- The repro scripts lived in a session scratch directory and were not
  committed. Each finding describes its repro well enough to turn it into
  a regression test when it's fixed.

## High

### 1. Load keeps the previous avatar's costume and Expression hotkey assignments

[`control_panel_window.py:3380`](../../src/unicorn_cloak/control_panel_window.py#L3380)
(`_on_load`) copies `name`, `sprites`, `active_costume` and `zoom` from the
loaded rig into the live one, but not `costume_assignments` or
`expression_hotkeys`. After Load:

- the Costume Hotkeys and Expression Hotkeys tabs show the *old*
  avatar's rows, pointing at sprite IDs that may not exist in the new one
- Shift+number fires the old avatar's expressions
- the next **Save** writes the old assignments into the new file, destroying
  the ones it had

**Repro:** open a test rig with a slot-0 pair and a `("Mouth", "Laughing")`
Expression hotkey, then Load `unicorn-demo.uc`. The rig still holds
`[(1, 2)]` / `[("Mouth", "Laughing")]` instead of the demo's
`[(2, 6), (5, 3), (7, 7)]` / `[("Eyes", "Open")]`. After Save, the demo
file on disk has the wrong assignments.

The hot-reload handler in
[`__main__.py:160`](../../src/unicorn_cloak/__main__.py#L160) has the same
omission (see #15). Fix: copy every `AvatarRig` field on load and reload,
ideally through one shared "replace rig contents" helper so a new field
can't be missed in one place.

### 2. Undo after Load overwrites the loaded file with the previous avatar

`_on_load` calls `push_undo_snapshot()` before swapping in the new avatar,
then re-points `_current_avatar_path` to the new file. Undo restores the
old avatar's sprites but not the path (or `rig.name`), so the title bar
reads `b2.uc*` while the rig holds avatar A. **Save then overwrites B
with A.** Only the single `.bak` generation protects it.

**Repro:** a panel holding a 2-sprite rig, Load the 17-sprite demo copy,
Undo, Save. The file on disk now has 2 sprites.

Fix: treat Load as a history boundary (clear the undo and redo stacks
instead of pushing a snapshot), or include the avatar path and name in
the snapshot so Undo restores them too.

### 3. Save triggers the app's own hot reload, resetting the live costume

`save_avatar` writes via temp file + `os.replace`, which
`QFileSystemWatcher` reports as a change to the watched avatar file. About
200 ms after every **Save**, `on_avatar_file_changed_on_qt_thread`
([`__main__.py:160`](../../src/unicorn_cloak/__main__.py#L160)) reloads the
file and:

- sets `rig.active_costume = reloaded.active_costume`. That is always 0,
  because `active_costume` isn't persisted, so **pressing Save while live
  in costume 4 snaps the Render Window (and OBS) back to costume 1**
- calls `refresh_after_external_change()`, which deselects the sprite
  being edited and calls `render_window.rebuild()`, resetting every
  sprite's drag, rotation and stretch state mid-stream

**Repro:** watch a copy of the demo with `AssetWatcher`, set
`active_costume = 3`, `save_avatar(...)`, and pump events for 1 s. The
reload signal fires, and the reloaded rig's `active_costume` is 0.

Fix: ignore self-writes (record the saved file's mtime and size, or its
content hash, and skip a reload that matches), and never overwrite
`active_costume` from a reload.

### 4. Variant alternation blanks sprites that share a band

The renderer decides how many variants a band has by counting eligible
*sprites* with a matching state, across the *whole rig*:

- [`render.py:521`](../../src/unicorn_cloak/render.py#L521)
  (`_talk_variant_sibling_count`) for the talk axis
- [`render.py:559`](../../src/unicorn_cloak/render.py#L559) for the blink axis
- [`control_panel_window.py:2746`](../../src/unicorn_cloak/control_panel_window.py#L2746)
  (`_preview_variant_counts`) for the Edit canvas preview

It then cycles an index `0..count-1` and shows only sprites whose
`variant` equals it. Two sprites in the same band with the same variant
(the default is 0) therefore make count = 2, and on index 1 *neither*
shows. The same happens when variants are non-contiguous (0 and 2).

Realistic triggers:

- separate left and right eye sprites, both "Only eyes open". Both eyes
  vanish for about 6.7 s of every 13.3 s at the default
  `eye_variant_hz = 0.15`
- a mild mouth plus any other talk-gated accessory (eyebrows, a "talking"
  effect). Both flicker off at 8 Hz while talking
- **Duplicate** on a mouth or eye sprite creates exactly this collision

**Repro:** four sprites (two eyes with `blink_state=1`, a mouth and
brows with `talk_state=1`), all at variant 0, in different groups. Over
10 s of simulated frames at talk level 1, all four hit opacity 0
repeatedly.

`rig_lint._check_variant_collisions`
([`rig_lint.py:117`](../../src/unicorn_cloak/rig_lint.py#L117)) only
checks within one group or parent bucket, so it reports nothing for the
cross-group case. Its message ("they'll always show/hide together instead
of alternating") also understates the same-group case: they all disappear
together.

Fix: build each band's alternation pool from the *distinct* `variant`
values actually present (cycle through that sorted set), scoped per
`group_name` rather than rig-wide. Then extend the lint to match.

### 5. Export Snapshot stacks mutually exclusive sprites

`snapshot._rest_alpha` ([`snapshot.py:25`](../../src/unicorn_cloak/snapshot.py#L25))
calls `sprite_alpha` without `manual_driven`, `manual_active` or any
variant counts. So:

- a Manually driven sprite (the demo's "Eyes: Open") counts as always visible
- every variant of an "eyes open" band shows at once

**Repro:** on `unicorn-demo.uc`, costume 0, the snapshot includes
`eyes_regular.png`, `eyes_open.png` *and* `eyes_squint.png`, three eye
layers drawn on top of each other.

Fix: pass `manual_driven=sprite.manual_driven`, `manual_active=False`, and
restrict each band to its lowest variant (variant 0, or the band's
minimum).

Related, lower severity (code-verified):

- A child of an invisible parent is attached to its *grandparent's* item
  ([`snapshot.py:91`](../../src/unicorn_cloak/snapshot.py#L91)), so its
  Position (authored in the parent's space) lands in the wrong place.
  Build an empty, transform-only item for invisible parents instead.
- The snapshot doesn't set `ItemStacksBehindParent` for negative `z_index`
  or apply `clipped`, unlike `render.py`, so hair-back layers can export in
  front of the head.

### 6. Envelope loop applies gain twice

`AudioManager._handle_volume_from_source`
([`audio_manager.py:297`](../../src/unicorn_cloak/audio_manager.py#L297))
multiplies by `config.audio.gain` and *then* records the value. The loop
([`audio_manager.py:223`](../../src/unicorn_cloak/audio_manager.py#L223))
feeds those already-gained values back into the same handler, which
multiplies by gain again.

**Repro:** gain 2.0, raw input 0.05. Live, the envelope sees 0.1; the loop
replays 0.2.

At any Sensitivity other than 1.0, thresholds tuned against the loop,
which is the feature's whole purpose, are off by a factor of gain. Fix:
record the raw pre-gain value, or have the loop bypass the gain step.

### 7. Any property edit silently rounds and clamps transform fields

`_on_property_changed`
([`control_panel_window.py:3128`](../../src/unicorn_cloak/control_panel_window.py#L3128))
writes *every* field from its widget back into the sprite, whichever
field actually changed. The Position, Offset, Rotation and Scale
spinboxes come from `_spin()`, which never calls `setDecimals`
(QDoubleSpinBox defaults to 2). Position and Offset are also range-limited
to ±4000 ([`control_panel_window.py:1489`](../../src/unicorn_cloak/control_panel_window.py#L1489)),
while canvas drags and corner-scale drags write unrounded, unbounded floats.

**Repro:** sprite with scale 0.843, position (12.3456, −4500), rotation
7.125. Change only its **Talk state**. The result is scale 0.84, position
(12.35, −4000), rotation 7.13.

This is the same scale class as the sunglasses and head values the owner
reported on 2026-09-20. Fix: write back only the field whose signal fired,
or give these spinboxes enough decimals (4 or more) and ranges that cover
anything the canvas can produce.

### 8. OBS mute can get stuck on

`__main__.py` only forwards `mute_changed` to `window.set_muted`
([`__main__.py:207`](../../src/unicorn_cloak/__main__.py#L207)).
`ObsLinkManager._stop()` and `ObsMuteWatcher`'s disconnect path emit
`connection_changed(False)` but never `mute_changed(False)`. The Control
Panel's own handler
([`control_panel_window.py:3613`](../../src/unicorn_cloak/control_panel_window.py#L3613))
resets *its label's* muted flag on disconnect, so the UI reads
"Not connected" while `RenderWindow.muted` stays `True`.

The result: mic muted in OBS, then OBS closed (or the checkbox unticked,
or the Input name changed), and **the avatar never opens its mouth again**
until OBS reconnects and reports that input unmuted, or the app restarts.
Unticking the feature, the obvious fix attempt, doesn't help.

Fix: on `connection_changed(False)`, also call `window.set_muted(False)`
(or have `ObsLinkManager` emit `mute_changed(False)` when it stops).

## Medium

### 9. Expression buttons lose their checked state while the expression stays live

`_refresh_expressions_section`
([`control_panel_window.py:3704`](../../src/unicorn_cloak/control_panel_window.py#L3704))
destroys and recreates every Expression toggle, all unchecked. It runs on
every property edit, Load and hot reload, and never reads back
`render_window.manual_overrides`.

**Repro:** on the demo, click "Eyes: Open", then change any sprite's
Variant. The button now shows off while the Render Window still forces
Eyes: Open. The first Shift+1 press re-checks the button with no visible
change; turning the expression off takes a second press.

Also, after Load, an override for a group name that also exists in the
new avatar stays forced with no visible control. Fix: restore each
button's checked state from `render_window.manual_overrides` when
rebuilding, and drop overrides whose group no longer exists.

### 10. A costume row's "Show" sprite isn't hidden in other costumes

The Help text ("Pick a sprite in **Show** — it's hidden everywhere else
and this hotkey shows it") and `AvatarRig.assign_costume_pair`'s own
docstring ([`rig.py:273`](../../src/unicorn_cloak/rig.py#L273)) both
promise that the Show-side sprite is hidden in every *other* slot. The
code only writes `costume_layers[slot] = True` for it, which a normal,
freshly added sprite already has.

**Repro:** two fresh sprites. `assign_costume_pair(1, hide_id=glasses,
show_id=bare_eyes)`. Costume 1 (index 0) still shows both glasses and bare
eyes.

It only appears to work in the demo because those sprites already carried
legacy `costume_layers` with zeros in the other slots. Separately, the
editor accepts the same sprite on both sides of a row; the demo file
contains a `(7, 7)` pair in slot 0, whose net effect is "hidden". Neither
case is flagged by Check for Issues.

### 11. Loop and file playback can drive the mouth at the same time

When a recording finishes, `_start_loop`
([`audio_manager.py:223`](../../src/unicorn_cloak/audio_manager.py#L223))
calls `_stop_file()`, which nulls `self._file` without emitting
`file_playback_stopped`. The file's own late `on_finished` is then
discarded by the identity check. The Play button never refreshes and
keeps saying **Stop**. Clicking it runs `play_file()`, which stops the mic
and any earlier file but not the loop
([`audio_manager.py:159`](../../src/unicorn_cloak/audio_manager.py#L159)),
so two background threads feed the envelope at once.

**Repro:** with a stub `FilePlayback`, play a file, record and finish a
loop, then click the (stale) "Stop" button. The result is
`is_looping=True` and `is_file_playing=True`.

Fix: `_start_loop` should emit `file_playback_stopped` when it stops a
file, and `play_file` should stop the loop.

### 12. Old `settings.json` crashes startup

`_migrate_raw_config` ([`config.py:86`](../../src/unicorn_cloak/config.py#L86))
`break`s at the first version with no registered migration. A version-0
file (no stamp) therefore never reaches migration 1 (`window.zoom`
removal), and `_merge` raises `ValueError: unknown WindowConfig
setting(s): ['zoom']` at launch.

**Repro:** a `settings.json` with no version stamp and
`"window": {..., "zoom": 1.5}` fails to load. The same file stamped
version 1 loads fine.

Fix: skip missing steps (`version += 1` and continue) rather than
stopping. More generally, `load_state` has no fallback for an unknown key
or unparseable JSON: any of those crashes startup even though a
`settings.json.bak` sits right next to it.

### 13. Gravity = 0 makes the avatar fly away

The Gravity field's range starts at 0.0
([`control_panel_window.py:1372`](../../src/unicorn_cloak/control_panel_window.py#L1372)).
With zero gravity, `bounce_step`
([`motion.py:259`](../../src/unicorn_cloak/motion.py#L259)) never decays
the upward velocity: after one bounce the avatar is about 2,500 px up
within 10 s, and `should_retrigger_bounce` never returns true again.
Fix: raise the minimum above zero, or clamp inside `bounce_step`.

### 14. The hot-reload watcher isn't re-pointed after Load or Save As

`AssetWatcher.watch_avatar_file` is only called once, at startup
([`__main__.py:157`](../../src/unicorn_cloak/__main__.py#L157)), and the
Control Panel has no reference to the watcher. After Load or Save As:

- the newly current file is never watched
- a change to the *old* file triggers a reload that reads
  `config.avatar_path`, i.e. the *new* file

Sprite PNG watches are also never updated for sprites added or replaced
through the Control Panel.

### 15. Hot reload drops state it shouldn't

`on_avatar_file_changed_on_qt_thread`
([`__main__.py:160`](../../src/unicorn_cloak/__main__.py#L160)) replaces
the rig's sprites without checking the dirty flag, so unsaved edits are
discarded with no prompt. It also leaves `_dirty` and the undo stack
untouched, so the title still shows `*` and Undo resurrects the
pre-reload sprites over the reloaded ones. Like #1, it doesn't copy
`costume_assignments` or `expression_hotkeys`, so hand-editing those in
the file is never picked up.

### 16. Load doesn't confirm, and I/O errors are silent

- `_on_load` swaps avatars even when the current one is dirty, with no
  Save/Discard/Cancel prompt. `confirm_and_quit` already has that dialog.
- `_on_save`, `_on_save_as`, `_on_load`, `_on_add` and `_on_replace` don't
  catch `OSError`, `json.JSONDecodeError` or `KeyError`. A failed save (an
  unwritable directory, a full disk) or a malformed load prints a
  traceback to the console and nothing else. For Save, the only clue is
  that the title's `*` stays. Only Export Snapshot shows an error dialog.

## Low

### 17. Loop playback uses the wrong frame time

During a loop neither `_mic` nor `_file` is set, so
`AudioManager.samplerate` and `blocksize`
([`audio_manager.py:113`](../../src/unicorn_cloak/audio_manager.py#L113))
fall back to 44100 and 1024. `update_speaking` then gets
`frame_seconds = 23.2 ms` for values recorded at 21.3 ms per block (a
48 kHz PipeWire mic), so Attack/Hold/Release behave about 9% differently
while tuning against the loop than live. Fix: store the frame time
alongside the recording.

### 18. Stop loop auto-plays a file source

`stop_loop` ([`audio_manager.py:190`](../../src/unicorn_cloak/audio_manager.py#L190))
calls `play_file()` whenever the source was "file", restarting the
recording from the beginning, even if it had finished or been stopped.
That is the same auto-play surprise commit `afd2ed0` removed from Rewind.

### 19. OBS Port spinbox restarts the watcher on every step

`obs_port.valueChanged` is wired straight to `restart()`
([`control_panel_window.py:1841`](../../src/unicorn_cloak/control_panel_window.py#L1841)).
Typing `4456` restarts the watcher four times, and each `stop()` joins the
thread for up to 2 s on the Qt thread. The other OBS fields use
`editingFinished`; Port should too.

### 20. Smaller edge cases (all code-verified)

- **Dangling references on delete.** Deleting a sprite leaves its pairs in
  `costume_assignments`: the editor row shows "—" while the pair is still
  saved, until that slot is next edited
  ([`rig.py:369`](../../src/unicorn_cloak/rig.py#L369)).
- **No-op undo entries.** Every mouse press on a canvas sprite pushes an
  undo snapshot, including a plain click-to-select, so Undo often appears
  to do nothing
  ([`control_panel_window.py:367`](../../src/unicorn_cloak/control_panel_window.py#L367)).
- **Short hotkey list crash.** A `settings.json` with fewer than 10
  `costume_keys` leaves `_costume_add_button_items` missing slots, so
  loading an avatar with assignments in those slots raises `KeyError`
  ([`control_panel_window.py:2024`](../../src/unicorn_cloak/control_panel_window.py#L2024)).
- **Unvalidated state values.** `load_avatar` accepts any `showTalk` or
  `showBlink` value. An out-of-range one (a hand-edited file) makes
  `axis_visible` raise on every frame, freezing the Render Window.
- **No threshold ordering checks.** Nothing enforces `mild_close ≤
  mild_open ≤ wide_open`, or `wide_close ≤ wide_open`; a crossed pair
  makes a band unreachable, or makes it flap.
- **Microphone thread restart.** `Microphone.stop()` gives up joining after
  2 s, and a following `start()` clears the *shared* stop event, which
  would un-stop a still-alive old thread and run two capture threads.
- **Loop busy-spin.** `EnvelopeLoopPlayback` busy-spins, flooding the Qt
  queue, if a recording's only sample sits at t ≈ 0 (a near-empty
  recording).
- **Media player leak.** `_clear_background_media` drops its reference to
  the `QMediaPlayer`, but the player is parented to the window and never
  `deleteLater()`'d, so one leaks per background switch.
- **Wheel direction.** A horizontal wheel or trackpad scroll
  (`angleDelta().y() == 0`) on the Edit canvas zooms *out*.
- **Settings write churn.** Every spinbox step writes `settings.json` with
  `fsync` plus a fresh `.bak` copy, so holding an arrow key writes dozens
  of times a second, and the `.bak` is only ever one step old.
- **Permissions and symlinks.** `save_avatar` and `save_state` write
  through `mkstemp`, which creates files `0600`. An avatar file loses its
  original permissions on first save, and a symlinked avatar path is
  replaced by a regular file.

### 21. Missing test module

`src/unicorn_cloak/spritesheet.py` has no `tests/test_spritesheet.py`.
CLAUDE.md's Testing rule requires one per module. (`slice_frame` with
`frames` greater than the image width silently returns an empty pixmap,
which such a test would catch.)

## Checked and ruled out

- **FilePlayback end-of-file race.** `_run` calls `process.terminate()` in
  its `finally` even after a clean EOF, so a spurious "ffmpeg exited with
  an error" seemed possible. Across 40 real ffmpeg runs on a short tone it
  never happened: `Popen.terminate` polls first, and ffmpeg has already
  exited once stdout closes. Not a bug in practice.
- **Blink chance of 0**, which would make `random.randrange(0)` raise every
  frame, can't be reached from the UI (minimum 10).
- **Escape bound as a costume hotkey** is rejected by the key-capture
  setter, and Escape is checked first in `RenderWindow.keyPressEvent`
  anyway.

## Suggested fix order

1. **#3 and #8** break a live stream directly: a costume reset on Save, and
   a mouth stuck shut. Both fixes are small.
2. **#1, #2 and #7** silently corrupt or overwrite avatar files.
3. **#4 and #5** are visible rendering errors that any reasonable rig
   (separate left and right eyes) will hit.
4. **#6, #9, #10 and #11** are feature-level bugs in tuning, expressions,
   costumes and playback.
5. Everything else.

Each fix should land with a regression test built from the repro
described above, per CLAUDE.md's Testing rule.

### D1 (High). Switching Microphone ↔ Desktop Audio keeps capturing the old device

`switch_to_desktop()` and `switch_to_microphone()`
([`audio_manager.py:174`](../../src/unicorn_cloak/audio_manager.py#L174))
both end in `_start_microphone()`, which returns immediately if a capture
is already running
([`audio_manager.py:363`](../../src/unicorn_cloak/audio_manager.py#L363)).
The Control Panel's `_on_audio_source_changed`
([`control_panel_window.py:3788`](../../src/unicorn_cloak/control_panel_window.py#L3788))
only re-syncs the dropdown's *display*; `_sync_audio_device_selection`
never calls `set_device()`.

So in the normal case (app running on Microphone, owner picks Desktop
Audio), the dropdown shows the desktop device but **the mic keeps driving
the mouth**. The same happens in reverse. Desktop Audio only really works
when the app starts up already set to it, or when coming from File or a loop.

**Repro:** with a stubbed `Microphone` recording its device, start on
Microphone (`Blue Microphones…`) and switch the UI to Desktop Audio (the
dropdown reads `Built-in Audio Analog Stereo`). Capture is still on
`Blue Microphones…`.

The existing tests only call `switch_to_desktop()` on a manager with no
capture running, which is why this got through. Fix: have both switch
methods stop any running capture first (or restart when the resolved
device hint changes), and add a test that switches mic → desktop → mic
with capture running.

### D2 (Medium-High). Desktop Audio + "System default" is the microphone

`resolve_input_device(None)`
([`audio.py:197`](../../src/unicorn_cloak/audio.py#L197)) picks the first
usable *input*. On this machine that's `Blue Microphones Analog Stereo`
(checked against the live device list). `desktop_device` defaults to
`None`, so **choosing Desktop Audio out of the box captures the mic**,
and nothing in the UI says so.

Fix: for the desktop source, don't offer "System default". Either require
an explicit pick (showing "Choose an output to capture…" until one is
made) or label the fallback honestly.

### D3 (Medium). A missing desktop device silently falls back to the mic

An unmatched hint also falls through to that same default
([`audio.py:213`](../../src/unicorn_cloak/audio.py#L213)). That happens on
the first open, and in `Microphone`'s reconnect loop if the device
vanishes mid-stream (e.g. an HDMI or USB audio output unplugged).
Confirmed at the resolution level: the hint `"Some Unplugged Sink"`
resolves to `Blue Microphones Analog Stereo`. The avatar then starts
lip-syncing to the owner's voice while "Desktop Audio" is selected.

For the desktop source the right move is to report an error and keep
retrying the chosen device, not swap in a mic.

### D4 (Medium). OBS mute awareness applies to every source

`on_mute_changed_on_qt_thread`
([`__main__.py:233`](../../src/unicorn_cloak/__main__.py#L233)) forces the
mouth closed whenever the configured OBS input is muted, whatever the
audio source. With Desktop Audio (or File) driving the avatar, muting
your *mic* in OBS also silences an avatar that's following game or video
audio the stream can still hear. This needs an owner decision: gate it on
`source == "microphone"`, or add a per-source toggle.

### D5 (Low)

- **Missing docs.** Neither the Help window nor the README mentions
  Desktop Audio or the Device dropdown.
- **Substring matching.** Device hints are matched by substring, first
  match wins. No names collide on this machine today, but a device whose
  name contains another's (`"USB Audio"` and `"USB Audio Pro"`) would open
  the wrong one. Prefer an exact match, and fall back to substring only
  for hand-edited hints.
- **Shared thresholds.** Gain, gate and threshold values are shared by all
  sources, but voice and game/music audio need very different values
  (music keeps the mouth open constantly at voice settings). See E1 below.
